01/09Introduction

Asynchronous Back Testing Engine

The business problem

Pricing that is too tight can erode hedging margins; pricing that is too wide can discourage client flow. A single spread structure can also misprice different trade sizes.

How it works

The engine groups historical client trades into six volume tiers, L1–L6, and evaluates proposed spread structures. Client fills and broker hedge orders run on separate timelines, with hedges sliced into smaller orders.

What it enables

Teams can compare pricing scenarios, inspect revenue and estimated hedging costs by tier, and identify pricing imbalances before changing production settings. Results are scenario estimates rather than guaranteed trading outcomes.

MBG Data Platform

The business problem

Trading and operational data arrives from multiple platforms and systems. Trading, Risk, and Compliance teams need consistent, reliable datasets for analysis and reporting.

How it works

AWS ingestion and CDC pipelines feed a Medallion lakehouse. PySpark handles transformation and deduplication, while dbt models implement incremental processing, star schemas, and SCD Type 2. Airflow and Step Functions coordinate delivery.

What it enables

Analytics-ready data is supported by automated quality checks, Lake Formation governance, IAM access controls, and lineage. Terraform and GitHub Actions provide reproducible infrastructure and deployments, with FastAPI serving curated datasets.

ZeroMQ Trading Data Pipeline

The problem

Trading data was spread across MySQL databases for more than 20 clients, with each client operating up to 20 trading servers. Separate connections sent this data directly to kdb+. In our environment, this connection pattern was associated with crashes and inconsistent data, making ingestion harder to operate reliably.

The architecture

We introduced a Python pipeline using PyZMQ and ZeroMQ’s PUSH/PULL pattern. Source processes send records into one shared receiving service for all clients. That service writes to kdb+ through one connection, centralising write handling instead of maintaining a direct connection from every source.

Python + ZeroMQSource PUSH processes · shared PULL receiver
kdb+One shared connection · keyed upserts

How incremental ingestion works

  1. A continuous Python polling loop reads the maximum stored creation timestamp from kdb+ for the relevant client and server.
  2. The source query selects MySQL records where creation_time >= max_time. Including the boundary allows records with the same timestamp to be read again.
  3. Records pass through ZeroMQ to the shared receiver.
  4. The receiver upserts records using the combined key of client ID, order ID, and server ID, so repeated records update the same stored row.
  5. If a kdb+ write fails, the receiver retries that batch successfully before proceeding with newer batches.

Why these choices mattered

A timestamp per client and server keeps one source’s progress separate from another’s. Inclusive polling and keyed upserts work together: the pipeline can reread the timestamp boundary without creating duplicate stored rows. Blocking retries keep newer writes from overtaking a failed batch during normal operation.

The result

The shared service and single kdb+ connection worked reliably in our deployment and addressed the instability we had seen with separate source connections. The improvement is based on operational experience; throughput, latency, and incident-reduction measurements are not included in this case study.

Recovery boundaries and trade-offs

ZeroMQ accepting a message does not by itself confirm that kdb+ has stored it. Restart recovery also depends on how pending batches are retained or recovered from MySQL. A maximum creation timestamp can miss older rows that become visible after the timestamp advances, and creation-time polling alone does not capture later updates or deletions.

The shared writer simplifies connections but is also a common failure point. A blocked batch can delay other clients. These boundaries matter when evaluating durability, monitoring, and future recovery improvements; this design is not presented as an exactly-once or zero-data-loss guarantee.

Technical references

Implementation details above describe our deployment. Messaging and acknowledgement boundaries are documented in the ZeroMQ socket reference, ZeroMQ send reference, and KX IPC documentation.

MarketSage Analytics

The business problem

Financial analysis draws on different data sources and methods. This project brings those inputs together so research, indicators, and portfolio views can be reviewed in one place.

How it works

LangGraph coordinates the agents using Groq’s Llama model. FastAPI exposes their analysis to the React frontend. A mock-LLM fallback supports offline development.

What it enables

Users can explore market research and financial indicators through a single application. The project is containerised with Docker and designed for deployment to Hugging Face Spaces.

Real-Time Anomaly Detection

The business problem

Streaming analysis needs consistent input data and a reliable path from ingestion to results. This project combines those stages in an end-to-end pipeline.

How it works

The pipeline uses Kafka, PySpark, and ClickHouse alongside Parquet storage. It supports batch and streaming processing, with FastAPI providing the serving layer.

What it enables

The project provides a containerised workflow for ingesting records, detecting anomalies, and exposing results. Automated tests and data-quality gates check the pipeline along the way.
